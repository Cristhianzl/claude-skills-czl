description: Langflow facts the context sweep needs — which CI jobs run PostgreSQL tests, who owns boot-sweep transactions, who else writes the user row, and the established lock/commit/migration idioms

Verified in the code on `release-1.14.0` (Nov 2026); re-check the line numbers when they drift. **Why:** two PRs (agentic variable seeding, flow description index) passed a pre-push review and still drew seven requested changes, all of which needed one of these facts. **How to apply:** use them in the sweeps of `references/context-sweep.md` whenever a PR touches PostgreSQL tests, startup seeding, the `user` row, locks, or Alembic.

- **PostgreSQL tests only run in CI when their file is listed by name.** Two different variables enable them, set by two different workflows, and both workflows run explicit file lists: `LANGFLOW_TEST_DATABASE_URI` in `.github/workflows/migration-validation.yml` (the migration steps), and `LANGFLOW_TEST_POSTGRES_URL` in `.github/workflows/component-compatibility.yml`. A new test gated on either one skips its PostgreSQL arm in CI until its file is added to the matching step — and the SQLite arm often passes even without the fix.
- **Boot sweeps run in one transaction.** `initialize_agentic_global_variables` is called inside a single `session_scope()` from `main.py` (~552) and `preload.py` (~282): anything a per-user step locks stays locked until the whole sweep commits.
- **The `user` row has other writers on hot paths.** Login updates `last_login_at` through `update_user_last_login_at` (`services/database/models/user/crud.py`), also called from external-token auth (`services/auth/service.py`, ~1006). A boot-time lock on user rows makes those logins wait.
- **Established idioms to compare against.** Per-user commits for sweeps: `VariableService.initialize_all_user_variables` commits each user separately. Dialect-neutral row lock: `services/triggers/locking.py` writes a non-key column (`values(updated_at=Trigger.updated_at)`) with `synchronize_session=False`. Alembic is pinned `>=1.13`, so `create_index(..., if_not_exists=True)` / `drop_index(..., if_exists=True)` are available; migrations `c3e1d5a7f902` and `1d28fd31a982` already pair them.
- **The Kubernetes variable store addresses secrets by the ID's type.** `services/variable/kubernetes_secrets.py:encode_user_id` maps a `UUID` to `uuid-<id>` and a string to a different, sanitized name — rebinding `user_id` from `str` to `UUID` mid-function makes later reads and writes hit different secrets.
